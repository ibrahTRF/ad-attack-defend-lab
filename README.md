# Attack and Defend Own AD — Lab Write-Up

Home lab project | VMware Workstation | Windows Server 2022 (DC01) + Kali Linux

## 1. Objective

This project simulates a small Active Directory environment, attacks it as an adversary using realistic techniques, then switches to defense to find the evidence and remediate the underlying misconfigurations — bridging IT support/sysadmin fundamentals with offensive and defensive security.

## 2. Lab Environment

- **DC01:** Windows Server 2022, promoted to DC for `lab.local`, running AD DS and DNS
- **Kali Linux:** attacker/analysis box (Kerbrute, Impacket, hashcat, bloodyAD)
- **Network:** both VMs on VMware host-only VMnet1 (192.168.116.0/24), chosen specifically because it has no path to the internet — this guarantees attack traffic stays fully contained even by accident, which matters far more here than in a routine lab

## 3. Phase 0 — Network Isolation

Both VMs initially sat on VMware's NAT network, which routes traffic out to the real internet — unacceptable once live attack tooling is involved. They were moved to the isolated host-only network instead. That move forced several follow-on changes, each with a reason:

- **DC01's static IP** had to be set outside the DHCP-assigned range on the new network, because a DNS server needs a predictable address — clients can't reliably find a DNS server whose address might change.
- **DC01's own DNS client setting** had to point at itself at the new address, since a domain controller is normally also its own DNS server.
- **Kali's DNS resolution** was pointed at DC01 via NetworkManager, with `ignore-auto-dns` set — without that flag, NetworkManager would silently overwrite the manual setting with a DHCP-supplied one on the next reconnect or reboot, quietly breaking the lab later.

**Troubleshooting:** after the move, `dig` queries from Kali to DC01 timed out even though DC01's DNS service was running and the firewall rule for it was correctly enabled. Working through it systematically (service status, firewall rule, firewall scope, subnet mask) ruled each out in turn. The actual cause: the failing queries were for *external* domains (e.g. google.com), which DC01 can't resolve because its configured forwarders are unreachable on a deliberately internet-isolated network. That's expected behavior, not a defect — internal resolution (`dig @<DC01-IP> lab.local`) and `dcdiag` were both confirmed clean, which is what actually mattered for the project.

### Step-by-step

1. In VMware, open each VM's **Settings → Network Adapter** and switch it to **Host-only (VMnet1)**.
2. Open VMware's **Virtual Network Editor** to confirm VMnet1's subnet range and whether it has a gateway.
3. On DC01, open the network adapter's IPv4 properties and set a static IP outside the DHCP range (e.g. `192.168.116.20/24`), with **Preferred DNS server** pointing at that same address.
4. Run `ipconfig /registerdns` on DC01 to republish its own DNS records at the new address.
5. On Kali, check the current DNS setting with `cat /etc/resolv.conf`, then find the connection name with `nmcli connection show`.
6. Point Kali at DC01 for DNS:

```
sudo nmcli connection modify "Wired connection 1" ipv4.dns "<DC01-IP>"
sudo nmcli connection modify "Wired connection 1" ipv4.ignore-auto-dns yes
sudo nmcli connection up "Wired connection 1"
```

7. Verify: `dig @<DC01-IP> lab.local` from Kali should return an answer, and `dcdiag` on DC01 should come back clean.

## 4. Phase 1 — Enumeration

The tools were chosen and ordered specifically so that each step only required what the previous step had already produced — a realistic zero-knowledge-to-credentialed progression, not an arbitrary list:

1. **enum4linux** first, because it needs no credentials at all and gives broad situational awareness (domain info, shares, password policy) before committing to anything targeted.
2. **Kerbrute** next, because of a quirk in Kerberos: the server responds differently to a username that exists versus one that doesn't, even with no password supplied — so valid usernames (and which accounts have pre-authentication disabled) can be confirmed without ever guessing a password or risking an account lockout.
3. **Impacket's `GetNPUsers.py`**, run only against accounts found to have pre-authentication disabled, because Kerberos normally requires proving password knowledge *before* responding — skip that check, and the server will hand back data encrypted with the user's password-derived key to anyone who asks.
4. **hashcat**, to attack that encrypted data offline. Offline cracking is used specifically because it needs no further contact with DC01 — no lockout risk, no logs generated by the guessing itself.
5. **bloodyAD**, last, because it's the first tool in the chain that actually requires a valid credential to do anything — it authenticates over LDAP and can both enumerate and modify objects once it has one.

### Step-by-step

1. `enum4linux -a <DC01-IP>` (or `enum4linux-ng`) for a broad first pass.
2. `kerbrute userenum --dc <DC01-IP> -d lab.local userlist.txt` to confirm valid usernames and flag any with pre-authentication disabled.
3. For any pre-auth-disabled account, extract its hash:

```
python3 GetNPUsers.py lab.local/ -usersfile userlist.txt -no-pass -dc-ip <DC01-IP>
```

4. Save the returned hash to a file, then attempt to crack it offline:

```
hashcat -m 18200 hash.txt /usr/share/wordlists/rockyou.txt
```

## 5. Phase 2 — Attack

### 5.1 Setup

Test account `harry4real` was deliberately given two separate weaknesses at once — Kerberos pre-authentication disabled, and `GenericAll` over the Domain Admins group — rather than just one. This mirrors how real compromises usually work: an attacker chains an initial-access technique (stealing a credential) into a privilege-escalation technique (abusing what that credential is allowed to do), rather than relying on a single isolated flaw.

### Step-by-step

1. On DC01, open **Active Directory Users and Computers**.
2. Right-click the Users container → **New → User**, create `harry4real` with a password.
3. Open the account's **Properties → Account** tab and check **"Do not require Kerberos preauthentication"**.
4. Enable **View → Advanced Features** in ADUC (off by default).
5. Open **Domain Admins → Properties → Security → Advanced → Add**, and select `harry4real` as the principal.
6. Set **Type** to **Allow**, **Applies to** to **"This object only"**, and check **Full control**.
7. Click **OK/Apply** to save.

### 5.2 AS-REP Roasting (recon)

Kerbrute and `GetNPUsers.py` confirmed the account was roastable and extracted its AS-REP hash, proving the misconfiguration is genuinely exploitable in principle. hashcat was then run against `rockyou.txt` and exhausted without cracking it. That matters: it shows the account's password was strong enough to independently resist the attack, even with the Kerberos setting itself left wide open. In other words, one control (password strength) compensated for the failure of another (pre-authentication) — a concrete example of defense in depth, not a dead end.

### Step-by-step

1. Confirm the account is roastable: `kerbrute userenum --dc <DC01-IP> -d lab.local userlist.txt`.
2. Extract the AS-REP hash: `python3 GetNPUsers.py lab.local/harry4real -no-pass -dc-ip <DC01-IP>`, and save the output to a file.
3. Crack it offline: `hashcat -m 18200 hash.txt /usr/share/wordlists/rockyou.txt`.
4. Check the result at any time with `hashcat -m 18200 hash.txt --show`.

### 5.3 ACL Abuse (exploit)

`GenericAll` over a group is effectively full ownership of that group's membership list: whoever holds it can add or remove members directly, no further permission needed. Using the account's known credentials, `bloodyAD add groupMember 'Domain Admins' 'harry4real'` exploited exactly that, adding the account to Domain Admins directly from Kali over the network — bloodyAD was used specifically because Impacket's `net.py` turned out to only support *enumerating* group membership in this environment, not modifying it.

Two errors came up along the way, each revealing something real:

- An `invalidCredentials` error, traced to an authentication mismatch and corrected.
- An `insufficientAccessRights` error, which on investigation showed the `GenericAll` permission hadn't actually been saved — ADUC hides the Security tab by default (View → Advanced Features enables it), and the permission's scope also needed correcting from "all descendant objects" to **"This object only"**, since a group object doesn't meaningfully have descendants the way an OU does.

### Step-by-step

1. Install the tool: `pip install bloodyAD` (or `pipx install bloodyAD` if pip refuses on an externally-managed environment).
2. Confirm it's working: `bloodyAD -h`.
3. Run the exploit:

```
bloodyAD -d lab.local -u 'harry4real' -p '<password>' -H <DC01-IP> add groupMember 'Domain Admins' 'harry4real'
```

4. Verify: check **Domain Admins → Members** in ADUC, or query it directly with bloodyAD's `get` command.

**Result:** full domain compromise, reached from an external, unauthenticated starting position, via a two-stage chain of credential access followed by privilege escalation.

## 6. Defense: Finding the Evidence

Reviewing DC01's Security event log, **Event ID 4672** ("Special Logon") appeared first — but it only records that an account logged on with notable privileges, not what it actually did, so it's a side effect rather than the real evidence. **Event ID 4728** ("A member was added to a security-enabled global group"), under Task Category Security Group Management, is the actual record: Subject `LAB\harry4real`, Group Domain Admins, Member added `harry4real`. Windows Server 2022 audits this category by default, which is why the event was present without any extra audit policy configuration.

This matters for detection: an alert rule watching specifically for Event ID 4728 against the Domain Admins group, triggered by any Subject that isn't a known administrator, is a realistic and directly usable SOC detection — because it targets the one unambiguous moment the attack actually changed something, rather than a side effect of getting there.

### Step-by-step

1. On DC01, open **Event Viewer → Windows Logs → Security**.
2. Use **Filter Current Log** and filter by **Event ID 4728**.
3. Open the matching event near the attack's timestamp.
4. Scroll the description text to read the **Subject**, **Group**, and **Member** fields.

## 7. Hardening and an Open Finding

**Kerberos pre-authentication** was re-enabled on the account — the direct reverse of the setting that made AS-REP roasting possible in the first place, and the simplest way to close that path entirely.

**The `GenericAll` ACE**, however, was already gone by the time the project returned to remove it manually — with no deliberate removal performed. The most likely explanation is **AdminSDHolder/SDProp**, a built-in AD mechanism that periodically (roughly every 60 minutes by default) reapplies a protected, known-good permission template to sensitive groups like Domain Admins, specifically to undo unauthorized ACL changes like the one made here. If confirmed, this is a genuinely useful finding: it shows AD has its own self-healing control against persistent ACL abuse on its most sensitive groups, independent of any manual fix — though it wasn't verified directly (e.g. by checking the AdminSDHolder object's own ACL), so it's flagged as the likely explanation rather than a settled one.

### Step-by-step

1. On DC01, open ADUC → `harry4real` → **Properties → Account** tab → uncheck **"Do not require Kerberos preauthentication"** → Apply.
2. Open **Domain Admins → Properties → Security → Advanced**, locate `harry4real`'s entry (if still present), select it, and click **Remove** → Apply.
3. Re-run the original exploit command to confirm it now fails with `insufficientAccessRights`.
4. Re-run `GetNPUsers.py` against the account to confirm it no longer returns a crackable hash.

## 8. Summary and Lessons Learned

- Built and troubleshot an isolated two-VM AD lab from first principles, including working through a non-obvious DNS/network-isolation issue by systematically eliminating causes rather than guessing — a realistic troubleshooting exercise in its own right.
- Executed a full, realistic attack chain (enumeration → credential access via AS-REP roasting → privilege escalation via ACL abuse), choosing each tool specifically for what it could achieve without requiring something from a later stage.
- Learned, concretely, that a single misconfiguration rarely tells the whole story: a weak Kerberos setting was independently mitigated by password strength, and a privilege-escalation path may have been independently undone by AD's own protective mechanisms. Real environments layer multiple controls, so assessing any one in isolation can be misleading.
- Identified and validated a specific, actionable detection signal (Event ID 4728 on Domain Admins) that maps directly onto a real blue-team use case, rather than a generic "turn on logging" recommendation.
- Practiced core AD administration (OUs, security groups, delegation, auditing, firewall configuration) throughout, directly relevant to an IT support/sysadmin role, with a clear, demonstrated bridge into security operations.

## 9. Next Steps

- Confirm the AdminSDHolder/SDProp theory directly, by inspecting the AdminSDHolder object's own ACL or correlating the timing against the \~60-minute SDProp interval.
- Re-test both attack paths after hardening to confirm they now fail cleanly, and capture that evidence.
